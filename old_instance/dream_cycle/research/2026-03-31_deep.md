## Paper 1: ERL — Experiential Reflective Learning for Self-Improving LLM Agents
**arXiv: 2603.24639 | Published at ICLR 2026 MemAgents Workshop**
**Relevance: 5/5**

### Core Technique
ERL builds a persistent "heuristic pool" from past task trajectories. After each task:
1. The agent reflects on the trajectory (what it did, what succeeded, what failed)
2. Extracts distilled heuristics — not raw trajectories, but actionable strategic principles
3. Stores them in a persistent pool (markdown file or DB)

At task time:
1. LLM scores stored heuristics for relevance to the current task
2. Top N heuristics are injected into the context as "lessons learned"
3. Agent proceeds with this guidance — no fine-tuning required

### Why Raw Trajectories Don't Work
ERL found that injecting raw trajectories as few-shot demonstrations *hurt* performance (-1.9% vs baseline). The distillation step is crucial — raw trajectories are too verbose and too specific. Heuristics provide:
- Transferable abstractions (not task-specific)
- Positive lessons AND failure modes
- Context-efficient representations

### Key Results
- GAIA2 benchmark: 56.1% success rate vs 48.3% baseline = +7.8% lift
- Outperforms ExpeL and AutoGuide (prior experiential methods)
- Works even without reward signals (drops to 51.2%, still beats baseline)
- Works on single-attempt trajectories — no repeated execution needed

### How This Changes George

**George does not currently have a heuristic pool.** Each task (trading round, podcast generation, research, dream cycle) is approached from scratch. George has MEMORY.md for facts and context, but no structured collection of "lessons learned from doing tasks."

Concretely, George has encountered:
- Podcast audio pipeline failures → fixes discovered, some generalize beyond podcasts
- LLM signal filtering hurting PEAD → generalizes to "don't filter event-driven strategies with technical LLM agents"
- Container sys.path mismatches → generalizes to "always use explicit --target= path, never --user"
- X.com scraping failure → generalizes to "prefer WebSearch over browser for high-auth-wall sites"

These should be stored as heuristics, not just task-specific fixes.

**Proposed implementation:** Create `/workspace/group/heuristics.md` with structured heuristics organized by domain (coding, research, trading, tools, agents). Each heuristic: title, lesson, when-to-apply. In CLAUDE.md, add instruction to retrieve relevant heuristics at task start.

### Iteration: Follow-up Research
- Related: ICLR 2026 Workshop on AI with Recursive Self-Improvement — confirms this is the frontier of agent research
- Related: ExpeL (earlier method ERL beats) uses cross-task aggregation and loses granularity — ERL's single-attempt per-task approach is more practical for George's scale
- Implementation consideration: George doesn't need ML-based heuristic scoring. Simple keyword matching or LLM-based relevance scoring at task start is sufficient.

## Paper 2: TradingAgents v0.2.0 (arXiv:2412.20138, GitHub Trending March 2026)
**Relevance: 5/5**

### Core Architecture
Seven specialized agents in a trading firm structure:
1. **Fundamentals Analyst** — earnings, revenue, margins, guidance
2. **Sentiment Analyst** — social media, investor mood
3. **News Analyst** — breaking news, catalysts
4. **Technical Analyst** — price action, indicators, patterns
5. **Researcher** — synthesizes all analyst reports
6. **Trader** — makes the buy/sell/hold decision
7. **Risk Manager** — validates against current conditions before execution

Key design: quick-thinking models for data retrieval, deep-thinking models for analysis and decision. No GPUs required.

### Experimental Results
- Dataset: Multi-asset, multi-modal (prices, news, social, insider, fundamentals, technicals) Jan-Mar 2024
- Evaluation period: Jun-Nov 2024
- Daily decision cadence
- Results: "Notable improvements in cumulative returns, Sharpe ratio, and maximum drawdown" vs baselines (not publicly detailed in abstract, but v0.2.0 adds multi-LLM support)

### How This Changes George

**George has completed 27 backtesting rounds** on rule-based and ML strategies. The best strategies are identified. TradingAgents represents the logical next phase: instead of pure backtesting, use a multi-agent LLM layer as a **live decision filter** on top of the best strategies.

Specifically, George's PEAD portfolio (Sharpe 2.394, best overall) could benefit from:
- NewsAgent: Does the earnings gap have credible catalyst support?
- SentimentAgent: Is retail/institutional sentiment aligned with the gap direction?
- RiskAgent: Is current market regime (VIX, macro) conducive to PEAD plays?

**BUT** — R26 showed that IndicatorAgent filtering *hurts* PEAD. The TradingAgents approach adds fundamental/news/sentiment layers, not just indicator layers. This is the correct filter for PEAD (fundamental event-driven).

**Proposed Round 28:** Build a simplified TradingAgents-style overlay for PEAD signals:
- FundamentalsAgent: Revenue beat magnitude, earnings surprise %
- NewsAgent: Headline quality check (organic beat vs one-time item)
- Risk guardrail: Skip if VIX > 30 or market in downtrend
- Target: Does LLM-confirmed-PEAD improve on raw-PEAD Sharpe 2.394?

### Iteration: v0.2.0 Details
TradingAgents v0.2.0 (Feb 2026):
- Multi-provider LLM: GPT-5.x, Gemini 3.x, Claude 4.x, Grok 4.x, OpenRouter, Ollama
- Improved orchestration architecture
- GitHub: https://github.com/TauricResearch/TradingAgents

## Paper 3: POISE — Autonomous Discovery of LLM-RL Algorithms (arXiv:2603.23951)
**Relevance: 3/5 (meta-level)**

### Core Technique
POISE maintains a genealogically linked archive:
- Proposals → Implementations → Evaluations → Reflections
- Evolutionary search over algorithmic mechanisms coupled to training dynamics
- Each iteration informed by structured evidence from prior iterations
- Result: Pass@32 on AIME25 improves from 26.7% to 43.3% (+62% relative)

### How This Changes George

**George's dream cycle IS a POISE-style loop** — but without the genealogical linking. Each night:
- Scan (proposals) → Stage (implementations) → Apply → Reflect (next night)

What's missing: George doesn't link reflections back to which staged changes they resulted from, or track which improvements led to measurable gains. The changelog is linear but not genealogical.

**Practical improvement**: In staged change files, add a `derived_from` field linking each change to the research finding that inspired it. In the next night's reflection, check whether applied changes produced any measurable effect (did the podcast work better? did trading research advance?). This is POISE-lite genealogy at the level George needs.

**Already partially implemented**: Staged JSON files have `source` and `source_url` fields — this is the link back to the finding. The missing piece is forward-linking: reflection notes should explicitly reference prior staged changes and assess their impact.
