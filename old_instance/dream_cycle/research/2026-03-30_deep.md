## Paper 1: QuantAgent — Multi-Agent LLMs for Trading

*Source:* arXiv:2509.09995 | https://arxiv.org/abs/2509.09995
*Relevance: 5/5 — directly extends George's trading research*

### Core Technique

QuantAgent decomposes trading signal generation into four specialized LLM sub-agents:

- *IndicatorAgent*: Converts OHLC bars into technical indicators (noise-resistant numerical summary)
- *PatternAgent*: Identifies chart formations (peaks, troughs, consolidations) using multimodal LLM reasoning
- *TrendAgent*: Assesses directional bias from short-horizon price dynamics
- *RiskAgent*: Integrates all signals into risk/reward profile with natural-language rationale

Agents operate in a zero-shot setting — no fine-tuning required. Final decision is a consensus of the four agents, with traceable language-native reasoning.

### Key Results

- 80% directional accuracy on 4-hour intervals across Bitcoin, Nasdaq futures, and 8 other instruments
- Outperforms rule-based and neural baselines in zero-shot evaluation
- Accuracy degrades on sub-15-minute candles (noise floor issue)
- Natural-language rationale per trade — fully inspectable decisions

### How This Could Change How George Operates

*Immediate application:* George's current trading harness is purely rule-based (Python backtests, fixed indicator thresholds). QuantAgent suggests a hybrid approach:

1. Use the existing backtest harness to identify statistically significant setups (e.g., PEAD gap > 5%, SpinningTop at support)
2. Feed the top setups to an LLM agent for interpretation and confirmation
3. The LLM agent provides a natural-language rationale — useful for the Macro Regime Trading Dashboard product

*Product application:* The Macro Regime Dashboard could include an LLM-generated "signal narrative" — why the current regime favors or disfavors a trade. This is a differentiator vs. pure-quant dashboards.

*Limitation for George:* QuantAgent uses gpt-4o-mini + gpt-4o with image inputs (charts). George runs in a container without direct broker access or chart generation. A text-only version using indicator summaries (no images) would be needed.

### What to Follow Up

- QuantAgent GitHub: https://github.com/Y-Research-SBU/QuantAgent (open source, MIT-ish license)
- Explore whether a text-only IndicatorAgent + PatternAgent can work without image inputs
- Could be Round 25 of trading_eval: "LLM Signal Interpretation Round"

## Paper 2: mem-agent — Markdown-Based RL Memory for LLM Agents

*Source:* https://huggingface.co/blog/driaforall/mem-agent-blog
*Relevance: 5/5 — validates and extends George's existing memory architecture*

### Core Technique

mem-agent trains a 4B parameter LLM with GSPO (Group Sequential Policy Optimization variant) to perform three memory operations:

1. *Retrieve*: Find relevant past information from markdown files given a query
2. *Update*: Write new information to markdown files in a structured way
3. *Clarify*: Recognize ambiguity and ask for clarification before storing

The scaffold is inspired by Obsidian (markdown folder system) and uses Python tool calls to read/write files. Training uses synthetic data generated by GPT-4o for the three tasks.

A companion *mem-agent-mcp* server allows any LLM (including Claude) to use mem-agent as a background memory manager via MCP.

### Key Results

- On md-memory-bench (new benchmark): mem-agent significantly outperforms base LLMs at memory retrieval and update tasks
- The RL training teaches the agent *when not to write* (avoid cluttering memory) — a key insight
- Markdown files are human-readable, editable, and version-controllable — no hidden state

### How This Could Change How George Operates

*Validation:* George's MEMORY.md + SOUL.md + USER.md flat file architecture is correct. Three independent major projects (OpenClaw, memsearch, mem-agent) all converged on markdown files as the optimal memory format in 2026. No need to change the storage format.

*Improvement opportunity:* The three-operation framework (retrieve, update, clarify) is more disciplined than George's current ad-hoc memory updates. George should:
1. On each session start, *explicitly retrieve* relevant memory sections before answering
2. After learning new facts, *update* with a structured format (date-stamped, categorized)
3. When uncertain about what to remember, *clarify* rather than store everything

*CLAUDE.md improvement:* Add a memory discipline section — "before updating MEMORY.md, ask: is this fact stable? Is it durable? Would I need this in 30 days?"

*Linked insight from memsearch:* "Memories are just .md files — human-readable, editable, and version-controllable." George's architecture is correct.

### What to Follow Up

- mem-agent-mcp could be installed as an MCP server in the NanoClaw environment — enables RL-trained memory operations
- A-MEM (Zettelkasten linking) could complement flat storage by adding cross-references between related findings

## Paper 3: A-MEM — Agentic Memory with Zettelkasten Linking

*Source:* arXiv:2502.12110 | https://arxiv.org/abs/2502.12110
*Relevance: 4/5 — practical upgrade to George's flat memory architecture*

### Core Technique

A-MEM treats each memory note as a Zettelkasten card:
- Each note has *links* to related notes
- When a new memory is created, the system identifies 2-3 related existing memories and adds bidirectional links
- Retrieval traverses the link graph rather than doing isolated vector search

vs. flat storage (George's current approach): A-MEM found that linked memory improved multi-hop reasoning tasks by ~20% because related facts are co-retrieved.

### How This Could Change How George Operates

*Short term:* Not a breaking change — George's MEMORY.md could evolve to include cross-references. Example:

```
## Key Research Findings (Candlestick)
→ See also: MASTER_REPORT.md#candlestick
→ Related: Macro Regime findings (macro filter DOES NOT help candles)
→ Related: Product 1 (Macro Regime Dashboard uses these signals)
```

*Medium term:* Split MEMORY.md into topic files with cross-links:
- `trading_research.md` (findings + links)
- `products.md` (side hustle status + links to research)
- `systems.md` (automation status)
- `USER.md` (Kevin context)

Each file links to related files. George retrieves by topic, not full-document scan.

### Iterative Follow-Up

Checked MEMORY.md: currently ~60 lines, single file, no cross-references. Still manageable. Zettelkasten linking should be staged for when MEMORY.md exceeds 150 lines or after 5+ more research rounds.

*Verdict:* Stage as a low-risk memory architecture proposal — implement when MEMORY.md grows larger.
